    Domain Setup Steps

    Before deployment
    1. Purchase a domain from any registrar (Namecheap, GoDaddy, Route 53 Domains, etc.)
    2. Prefer an aged domain (6+ months old) — freshly registered domains have poor reputation
    3. Get the domain categorized as "Business Services" or "Technology" in web filters (e.g. Bluecoat, Fortiguard)
    4. Enter the domain above and save your configuration
    After deployment — pointing nameservers to AWS
    1. After Terraform finishes, it outputs 4 AWS nameservers for your domain, e.g.: ns-412.awsdns-51.com
      ns-1820.awsdns-35.co.uk
      ns-987.awsdns-59.net
      ns-143.awsdns-17.org
    2. Log into your domain registrar and find the Nameservers or DNS settings for your domain
    3. Change from the default nameservers to Custom nameservers and enter the 4 AWS nameservers from the Terraform output
    4. Save — DNS propagation takes minutes to 48 hours. Check progress: dig NS yourdomain.com
    5. Once propagated: SSL certificates auto-validate, DNS records go live, and CloudFront aliases activate — all automatic

    SSL/TLS Configuration

    SSL certificates for HTTPS on your redirectors. You do not need to purchase or manage certificates — both options below are free and automatic.

    SSL Handled by CloudFront + ACM

    Domain fronting is enabled — SSL is handled automatically at two levels:

    • Client → CloudFront: AWS Certificate Manager (ACM) auto-provisions a trusted certificate for free. Validated automatically via DNS — no action needed from you.
    • CloudFront → Redirector: The redirector uses a self-signed certificate. CloudFront does not verify origin certs, so this works without any setup.

    The settings below are disabled because domain fronting manages SSL end-to-end. If you disable domain fronting, these options will become available again.

    Both options are free. Let's Encrypt gives you a trusted cert that browsers accept without warnings.

    OPSEC: Self-Signed vs Let's Encrypt +

    Self-signed certificates are a major red flag for blue teams. Only use self-signed as a temporary fallback — always aim for Let's Encrypt in production.

    Risk Self-Signed Let's Encrypt
    Browser warnings "Your connection is not private" — suspicious if an analyst visits No warnings — looks like any legitimate site
    SSL inspection Corporate proxies (Zscaler, Palo Alto) flag or block self-signed certs Passes SSL inspection — trusted CA chain
    Threat intel scanning Shodan and Censys flag self-signed certs — routinely used to hunt C2 Blends in with millions of Let's Encrypt sites
    CT logs Not logged — no public record Cert appears in Certificate Transparency logs — blue teams can monitor for new certs on suspicious domains

    The only advantage of self-signed is that it's immediate (no DNS dependency) and doesn't appear in CT logs. Let's Encrypt is better in every other way. The redirector always starts with self-signed and upgrades to Let's Encrypt once DNS propagates.

    Required by Let's Encrypt for expiry reminders. OPSEC: This email is registered with Let's Encrypt's ACME servers — not visible in the certificate or CT logs, but stored in their account database. Use a burner/disposable email for red team ops.
    Leave this on. The redirector checks every 5 minutes and auto-requests a cert once DNS is ready.

    How it works

    1. On deploy, the redirector boots with a temporary self-signed cert so nginx can start immediately
    2. Once you point your domain nameservers to Route 53 (see Domain Configuration above), the redirector detects DNS propagation automatically (checks every 5 minutes)
    3. Let's Encrypt issues a free trusted certificate and nginx reloads — no manual steps
    4. Certificates auto-renew every 90 days
    CloudFront Domain Fronting (Advanced)

    Route C2 traffic through AWS CloudFront CDN to hide redirector IPs and blend with legitimate CDN traffic.

    Redirectors Only (default) + Domain Fronting
    Traffic path Beacon → Redirector IP → C2 Beacon → Front domain → CloudFront → Redirector → C2
    IP exposure Redirector IP visible in DNS and network logs Redirector IP hidden — only CloudFront IPs visible
    If domain blocked Beacons go dark. Blue team can also block the IP. Rotate to backup domain instantly (no redeploy)
    If IP blocked Must redeploy new redirectors (new IPs) — downtime N/A — redirector IP is never exposed to the target
    Complexity Simpler, deploys faster Extra 15-30 min deploy, may breach CDN ToS

    How Domain Fronting Works

    1. Your domains (primary + backups) become aliases on a CloudFront distribution
    2. DNS records point to CloudFront instead of redirector IPs
    3. Redirector IPs are hidden — only CloudFront IPs are visible to the target
    4. Front domain (e.g. grid.crowdstrike.com) is chosen operationally and configured in your CS malleable profile — NOT configured here
    Operational Checklist
    • Buy aged domain with good web categorization (Financial Services, Technology, etc.)
    • Point domain nameservers to Route 53 (or use Route 53 Domains)
    • Add backup domains above for rotation redundancy (recommended: 2-3)
    • Deploy — CloudFront distribution + ACM certificate auto-provisioned
    • Find frontable domains sharing CloudFront using FindFrontableDomains
    • Configure CS malleable profile: set front domain + Host header to your CloudFront domain

    Domain Rotation

    Backup domains (configured in Domain Configuration above) are pre-loaded as CloudFront aliases with valid SSL certificates.

    • If primary domain is burned: Switch CS profile to a backup domain — instant, no redeployment needed
    • To add new domains: Update backup domains above and redeploy (~15-30 min for CloudFront propagation)

    Technical Details

    • SSL: ACM auto-provisions certificates (free, no Let's Encrypt needed)
    • Caching: Fully disabled — all requests reach the origin (required for C2)
    • Security: Redirector HTTP/HTTPS locked to CloudFront IPs only
    • Deployment: CloudFront distributions take 15-30 minutes to deploy globally
    • ToS Warning: Domain fronting may breach CDN provider terms — plan for potential account termination
