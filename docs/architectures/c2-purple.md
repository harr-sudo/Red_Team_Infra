# C2 Purple Team - Redundant Team Servers

## Overview

The **C2 Purple Team** deployment runs **two Cobalt Strike team servers** behind a shared pair of redirectors, giving the engagement **redundancy and parallel-operator capacity**. It is the natural step up from [C2 Ad-Hoc](./c2-adhoc.md): same network shape, same redirector/attack-box pattern, but two team servers instead of one so a single server failure (or a single burned listener) does not take the whole operation down.

This mode maps to the Terraform `c2-purple` deployment type, which selects the **`redundancy`** C2 deployment mode (`c2_server_count = 2` by default).

## Architecture Components

### Infrastructure (Static IPs)

| Component | Type | Subnet | Private IP | Public IP | Purpose |
|-----------|------|--------|-----------|-----------|---------|
| **Redirector 1** | t3.small (nginx HTTPS) | DMZ (10.0.1.0/24) | 10.0.1.10 | EIP (Elastic IP) | Traffic forwarding (primary) |
| **Redirector 2** | t3.small (nginx HTTPS) | DMZ (10.0.2.0/24) | 10.0.2.10 | EIP (Elastic IP) | Traffic forwarding (backup) |
| **C2 Team Server 1** | t3.medium (Cobalt Strike) | Private 1 (10.0.10.0/24) | 10.0.10.10 | None | Primary CS team server |
| **C2 Team Server 2** | t3.medium (Cobalt Strike) | Private 2 (10.0.11.0/24) | 10.0.11.10 | None | Secondary CS team server (redundant) |
| **Attack Box** | t2.large (Windows 2022) | Private 1 (10.0.10.0/24) | 10.0.10.50 | None | CS Client GUI, red team tools |
| **NAT Gateway** | Managed | Public | — | Auto | Outbound-only internet for private instances |

The two team servers sit in **separate private subnets across two availability zones** (10.0.10.0/24 and 10.0.11.0/24), so an AZ-level disruption only affects one server. Both run an identical Cobalt Strike bootstrap from S3; the operator decides how to split listeners between them.

### Network Architecture

The VPC (`10.0.0.0/16`, region `eu-central-1`) uses the same three-tier layout as every C2 deployment:

```
C2 VPC: 10.0.0.0/16
├── DMZ Subnets (public): 10.0.1.0/24, 10.0.2.0/24
│   ├── Redirector 1 (10.0.1.10, EIP) ← Beacon traffic (port 443)
│   ├── Redirector 2 (10.0.2.10, EIP) ← Beacon traffic (port 443)
│   ├── Internet Gateway — bidirectional, public subnets only
│   └── NAT Gateway — outbound-only internet for private subnets
│
└── Private Subnets: 10.0.10.0/24 (AZ-a), 10.0.11.0/24 (AZ-b) — NO public IPs
    ├── C2 Team Server 1 (10.0.10.10) ← Cobalt Strike :50050 / listener :443
    ├── C2 Team Server 2 (10.0.11.10) ← Cobalt Strike :50050 / listener :443
    └── Attack Box (10.0.10.50)       ← Windows workstation (CS Client, tools)
```

**Internet Gateway vs NAT Gateway** — the IGW is bidirectional and serves the redirectors' EIPs (target beacon callbacks arrive here). The NAT Gateway is outbound-only and serves the private subnets (apt updates, S3 downloads, git clone). Nothing on the internet can initiate a connection to a team server or the attack box.

**Operator access does not touch the redirectors or the IGW.** The AWS-hosted **Dashboard Server** (its own VPC, peered with this C2 VPC) reaches both team servers (10.0.10.10, 10.0.11.10) and the attack box (10.0.10.50) directly over VPC peering. There is no per-deployment SSH-relay bastion.

### How Redundancy Works

Both redirectors can forward to **either** team server. The default nginx config (generated by `setup_redirector.sh`) points at the primary team server's listener, but the redundancy model gives you several operating options:

1. **Active/active** — split your listeners and beacons across both team servers from day one. Each server carries part of the operation; losing one halves capacity instead of ending the engagement.
2. **Active/standby** — run everything on Team Server 1 and keep Team Server 2 warm. If TS1 is burned or fails, re-point the redirectors' upstream block to 10.0.11.10 and resume.
3. **Profile separation** — run a different Malleable C2 profile per server (for example, a noisy profile on one and a long-haul profile on the other) so a single profile detection does not compromise both.

Because both servers live behind the same redirector EIPs and DNS, beacons do not need to know which server they ultimately reach — the redirector decides.

## Key Features

### 1. Two Team Servers (Redundancy Mode)
- **No single point of failure** for the C2 control plane
- **Parallel operators** — two team leads can run independent client sessions
- **AZ separation** — servers in 10.0.10.0/24 and 10.0.11.0/24 sit in different availability zones
- **Independent CS profiles** — isolate detection blast radius per server

### 2. Shared Redundant Redirectors
- **Two redirector instances** (10.0.1.10, 10.0.2.10), each with an Elastic IP
- **Single NIC + 1:1 EIP NAT** at the IGW — the EIP never appears on the instance itself
- Supports multiple domains and (optionally) domain fronting

### 3. Attack Box (Windows Workstation)
- **Windows Server 2022** optimized for red team operations (Defender disabled, server bloat removed)
- **Cobalt Strike Client GUI** pre-installed from S3, with a desktop shortcut to the primary team server (10.0.10.10:50050)
- **Red team tools** cloned to `C:\Tools`, empty `C:\Payloads` for staging, WSL2 + Ubuntu available
- Private subnet only (10.0.10.50) — reached via RDP tunnel through the Dashboard Server
- Toggleable with `enable_attack_box = true` (default)

### 4. Operator Access Patterns

The **Dashboard Server is the operator's entry point and jump host.** It lives in its own VPC (10.100.0.0/16) peered with this C2 VPC, so it reaches every instance directly — no SSH-hopping. All tunnels below run THROUGH the dashboard's EIP. The operator's laptop only runs a *dev* instance of the dashboard; production runs on this AWS server.

#### Option A: Dashboard Web UI (Recommended)
```bash
# Single tunnel from your laptop to the Dashboard Server
ssh -L 5000:localhost:5000 ubuntu@<dashboard-eip>

# Open the dashboard
http://localhost:5000
# In-browser terminal, topology, CS beacon management (both servers), deploy/destroy
```

#### Option B: CS Client to BOTH team servers through the Dashboard
```bash
# Tunnel both team servers at once through the Dashboard Server (peering routes the last hop)
ssh -i key.pem \
    -L 50050:10.0.10.10:50050 \
    -L 50051:10.0.11.10:50050 \
    ubuntu@<dashboard-eip>

# In the Cobalt Strike client, add two profiles:
#   Team Server 1 → 127.0.0.1:50050
#   Team Server 2 → 127.0.0.1:50051
```

#### Option C: RDP to Attack Box through the Dashboard
```bash
ssh -i key.pem -L 13389:10.0.10.50:3389 ubuntu@<dashboard-eip>
mstsc /v:localhost:13389
# Attack box has the CS Client pre-installed (shortcut → 10.0.10.10:50050)
```

## Deployment

### Configuration

```hcl
# terraform.tfvars
deployment_type = "c2-purple"   # Selects redundancy mode automatically

# Or explicitly:
c2_deployment_mode = "redundancy"
c2_server_count    = 2
c2_server_instance_type = "t3.medium"
redirector_count        = 2
proxy_redirector_instance_type = "t3.small"

# Network (defaults shown)
vpc_cidr             = "10.0.0.0/16"
public_subnet_cidrs  = ["10.0.1.0/24", "10.0.2.0/24"]
private_subnet_cidrs = ["10.0.10.0/24", "10.0.11.0/24"]

# Domains (REQUIRED for C2)
primary_domain_name = "operations.company.com"
backup_domains      = ["cdn.company.com"]

# Access Control
management_cidr_blocks = ["YOUR.PUBLIC.IP/32"]
```

### Via Web Application

1. Navigate to **Configuration**
2. Set **Deployment Type**: "C2 Purple Team"
3. Upload the **Cobalt Strike distribution** archive
4. Configure the **Domain** (required)
5. Click **Deploy** and wait ~15-20 minutes for provisioning (two team servers bootstrap in parallel)

### Via Command Line

```bash
cd terraform
terraform init -var-file=../configs/terraform.tfvars
terraform apply -var="deployment_type=c2-purple"
terraform output c2_connection_info
```

## Security Groups

### Redirector Security Group (`proxy_redirector_sg`)
```yaml
Inbound:
  - Port 80 (HTTP): 0.0.0.0/0          # or CloudFront prefix list if domain fronting
  - Port 443 (HTTPS): 0.0.0.0/0        # or CloudFront prefix list if domain fronting
  - Port 22 (SSH): management_cidr_blocks
  - Port 22 (SSH): dashboard_sg        # Dashboard Server via VPC peering (nginx config mgmt)
Outbound:
  - Port 443: c2_team_server_sg        # Beacon traffic to either CS listener
  - All traffic: 0.0.0.0/0             # Updates
```

### C2 Server Security Group (`c2_team_server_sg`)

Both team servers share this group:
```yaml
Inbound:
  - Port 443: proxy_redirector_sg   # Beacon traffic from redirectors (listener port)
  - Port 50050: dashboard_sg        # CS client tunnel from Dashboard Server (via peering)
  - Port 50050: attack_box_sg       # CS client from attack box (direct)
  - Port 50443: dashboard_sg        # CS REST API from Dashboard Server (via peering)
  - Port 22: dashboard_sg           # SSH management from Dashboard Server (via peering)
  - Port 22: attack_box_sg          # SSH from attack box
  - Port 22: management_cidr_blocks # SSH break-glass fallback
Outbound:
  - All traffic: 0.0.0.0/0
```

> Both servers being in one security group is intentional — they are peers. Network isolation between them is provided by separate subnets/AZs, not separate SGs.

### Attack Box Security Group (`attack_box_sg`)
```yaml
Inbound:
  - Port 3389 (RDP): dashboard_sg   # RDP tunnel from Dashboard Server (via peering)
  - Port 22 (SSH): dashboard_sg     # SSH from Dashboard Server (via peering)
  - Port 5985 (WinRM): dashboard_sg # TESTING ONLY
Outbound:
  - All traffic: 0.0.0.0/0
```

## SSL/TLS Options

Identical to the ad-hoc deployment — Let's Encrypt (standard), ACM with domain fronting (advanced), or self-signed (testing only). See the [C2 Ad-Hoc SSL/TLS section](./c2-adhoc.md#ssltls-options) for the full comparison and certificate flow diagrams. With two team servers, the redirectors still present a single public certificate; the choice of upstream server is internal to the redirector.

## When to Use / When to Upgrade

**Choose C2 Purple Team if:**
- You need redundancy for a medium-term engagement (2-4 weeks)
- Multiple operators require simultaneous, independent team-server sessions
- You want to isolate detection blast radius across two CS profiles
- A purple-team exercise needs a resilient C2 the blue team can probe without ending the test

**Upgrade to [C2 Full Red Team](./c2-full.md) if:**
- You want **phase-based** operations (staging / post-exploitation / long-haul) with a dedicated server per phase
- The engagement runs 4+ weeks with stricter OpSec compartmentalization
- You need distinct infrastructure lifecycles per operational phase

## Dashboard Server (Production Control Plane)

The dashboard runs on a dedicated AWS EC2 instance in its own VPC. It is the **production control plane and sole SSH jump host** — the operator's entry point for this and every other deployment. There is no per-deployment SSH-relay bastion. (The operator's laptop only runs a *dev* instance of the dashboard.)

### Dashboard Infrastructure

| Component | Type | VPC / Subnet | Private IP | Public IP | Purpose |
|-----------|------|-------------|-----------|-----------|---------|
| **Dashboard Server** | t3.medium (Ubuntu 22.04) | Dashboard VPC (10.100.0.0/16) / 10.100.1.0/24 | 10.100.1.10 | EIP (Elastic IP) | Web UI, SSH jump to all deployment instances |

### Network Connectivity

- **VPC Peering:** Dashboard VPC (10.100.0.0/16) <-> C2 VPC (10.0.0.0/16)
- Route tables on both sides carry the peering routes so traffic flows without NAT or tunnels

### Dashboard Access to C2 Instances

| Target | Ports | Purpose |
|--------|-------|---------|
| Redirector 1 (10.0.1.10) | SSH/22 | nginx config, health checks |
| Redirector 2 (10.0.2.10) | SSH/22 | nginx config, health checks |
| C2 Team Server 1 (10.0.10.10) | SSH/22, CS/50050, REST/50443 | Shell, CS client tunnel, REST API |
| C2 Team Server 2 (10.0.11.10) | SSH/22, CS/50050, REST/50443 | Shell, CS client tunnel, REST API |
| Attack Box (10.0.10.50) | SSH/22 | Management shell, RDP tunnel |

### Full Architecture with Dashboard

```
Operator Laptop  (dev instance of dashboard only — production runs in AWS)
   │ SSH key + IP allow-list, tunnel port 5000
   ▼
┌─────────────────────────────────────────────────┐
│  Dashboard VPC  10.100.0.0/16  (PRODUCTION)     │
│  Dashboard Server (10.100.1.10, EIP)            │
│    - Flask web UI on :5000                      │
│    - Control plane + SSH jump host              │
│    - REST API client to CS on :50443            │
└──────────────────────┬──────────────────────────┘
                       │ VPC Peering (10.100.0.0/16 ↔ 10.0.0.0/16)
                       ▼
┌─────────────────────────────────────────────────┐
│  C2 VPC  10.0.0.0/16                            │
│  DMZ (10.0.1.0/24, 10.0.2.0/24)                │
│    ├── Redirector 1 (10.0.1.10, EIP) ← :443    │
│    └── Redirector 2 (10.0.2.10, EIP) ← :443    │
│  Private (10.0.10.0/24, 10.0.11.0/24)           │
│    ├── C2 Team Server 1 (10.0.10.10)            │
│    ├── C2 Team Server 2 (10.0.11.10)            │
│    └── Attack Box (10.0.10.50)                  │
│  NAT Gateway → Internet (outbound only)         │
└─────────────────────────────────────────────────┘

Beacon traffic (from targets):
  Target → HTTPS :443 → Redirector 1/2 → C2 Team Server 1 or 2 :443
```

## Summary

C2 Purple Team is **two team servers behind redundant redirectors** — the same clean network shape as ad-hoc, with no single point of failure for the C2 control plane.

- ✅ Redundancy + parallel-operator capacity (~$30/month over ad-hoc)
- ✅ AZ-separated team servers (10.0.10.10, 10.0.11.10)
- ✅ Per-server CS profile isolation to limit detection blast radius
- ✅ Dashboard Server is the sole jump host — no per-deployment bastion

**Cost**: ~$190-230/month. Ideal for purple-team exercises and medium-term engagements that need resilience.
