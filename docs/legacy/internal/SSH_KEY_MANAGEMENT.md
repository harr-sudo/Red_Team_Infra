## Executive Summary

The current SSH key management implementation violates SSH security best practices by:
1. **Exposing private keys via web API** in plaintext JSON responses
2. **Storing private keys in Terraform state** (which may be shared/backed up)
3. **Distributing private keys across multiple systems** instead of generating them locally

This document proposes a revised architecture where private keys remain on the hosts that generate them, and only public keys are shared through the infrastructure chain.

### Critical Security Issues

#### 1. **Private Keys Exposed via Web API** 🔴 CRITICAL
- **File:** `webapp/backend/routes/deploy.py` (lines ~2060)
- **Issue:** Private keys returned in plaintext JSON responses
- **Code:**
```python
key_content = outputs.get("goad_jumpbox_ssh_private_key", {}).get("value")
key_content = outputs.get("goad_internal_ssh_private_key", {}).get("value")
key_content = outputs.get("goad_windows_ssh_private_key", {}).get("value")
```
- **Risk:** Any compromise of the web application or network traffic exposes all private keys

#### 2. **Private Keys in Terraform State** 🔴 CRITICAL
- **File:** `terraform.tfstate`
- **Issue:** All private keys stored in state file
- **Risk:** State files may be:
  - Committed to version control (if `.gitignore` misconfigured)
  - Backed up to unsecured locations
  - Shared among team members
  - Stored in remote backends without proper encryption

#### 3. **Private Key Distribution** 🟡 HIGH
- **File:** `terraform/modules/goad/scripts/jumpbox_init.sh`
- **Issue:** `internal_ssh` private key embedded in jumpbox via user_data
- **Code:**
```bash
INTERNAL_KEY="${internal_key}"
echo "$INTERNAL_KEY" > /home/ubuntu/.ssh/internal_key
```
- **Risk:** Private key transmitted through EC2 user_data (visible in AWS console)

#### 4. **Violation of SSH Key Principles** 🟡 HIGH
- Private keys should **NEVER** leave the host that generated them
- Current approach generates keys centrally and distributes them
- Breaks the fundamental trust model of SSH public key cryptography

## SSH Security Best Practices

### Core Principles

1. **Private Key Locality**
   - Private keys must be generated on the host that will use them
   - Private keys must NEVER be transmitted or shared
   - Private keys should be protected with filesystem permissions (600)

2. **Public Key Sharing**
   - Only public keys should be distributed
   - Public keys can be freely shared and stored
   - Public keys are placed in `~/.ssh/authorized_keys` on target hosts

3. **Key Lifecycle**
   - Each host generates its own key pair
   - Public keys are shared through secure provisioning mechanisms
   - Private keys remain on the originating host for their entire lifetime

4. **Access Chain Model**
   - User → Jumpbox (using user's private key, jumpbox has user's public key)
   - Jumpbox → Internal Hosts (using jumpbox's private key, internal hosts have jumpbox's public key)
   - No private keys should traverse this chain

#### Security Fix: Host Key Verification

The current implementation disables host key checking, which is vulnerable to MITM attacks:

```bash
# CURRENT (Insecure) - in jumpbox_init.sh lines 106-107, 113-114, 120-121:
StrictHostKeyChecking no        # ❌ Accepts ANY host key - vulnerable to MITM
UserKnownHostsFile /dev/null    # ❌ Never remembers host keys
```

**Proposed Fix** - Use `accept-new` for TOFU (Trust On First Use) security:

```bash
# PROPOSED (Secure):
StrictHostKeyChecking accept-new  # ✅ Accept on first connect, reject changes
# Remove UserKnownHostsFile line  # ✅ Persist known hosts for future verification
```

| Setting | First Connection | Subsequent Connections | MITM Protection |
|---------|------------------|------------------------|-----------------|
| `no` | Accept any key | Accept any key | ❌ None |
| `accept-new` | Accept & save | Reject if changed | ✅ After first use |
| `yes` | Reject unknown | Reject if changed | ✅ Full (requires pre-shared keys) |

**Note**: `accept-new` requires OpenSSH 7.6+ (Ubuntu 18.04+, all supported versions).

**Bootstrap Process (jumpbox_init.sh):**
```bash
#!/bin/bash
```

#### Windows SSH Key Configuration

Windows VMs require special handling for SSH authorized keys. The key location differs for administrators:

| User Type | Authorized Keys Location |
|-----------|-------------------------|
| Standard users | `C:\Users\<username>\.ssh\authorized_keys` |
| Administrators | `C:\ProgramData\ssh\administrators_authorized_keys` |

**Bootstrap Process (windows_init.ps1):**
```powershell
# Windows VM Bootstrap Script for SSH Key Configuration
# This script downloads the jumpbox public key and configures Windows OpenSSH

param(
    [string]$DeploymentBucket,
    [string]$DeploymentId,
    [string]$AwsRegion
)

# 1. Wait for jumpbox public key to be available in S3
$maxRetries = 30
$retryCount = 0
$keyDownloaded = $false

Write-Host "Waiting for jumpbox public key..."
while ($retryCount -lt $maxRetries -and -not $keyDownloaded) {
    try {
        Read-S3Object -BucketName $DeploymentBucket `
            -Key "keys/$DeploymentId/jumpbox_internal.pub" `
            -File "C:\temp\jumpbox_internal.pub" `
            -Region $AwsRegion
        $keyDownloaded = $true
        Write-Host "Public key downloaded successfully"
    } catch {
        Write-Host "Waiting for key... (attempt $retryCount of $maxRetries)"
        Start-Sleep -Seconds 10
        $retryCount++
    }
}

if (-not $keyDownloaded) {
    Write-Error "Failed to download jumpbox public key after $maxRetries attempts"
    exit 1
}

# 2. Ensure OpenSSH is installed and running
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType 'Automatic'

# 3. Configure administrators_authorized_keys
$sshDir = "C:\ProgramData\ssh"
$authKeysFile = Join-Path $sshDir "administrators_authorized_keys"

# Create directory if it doesn't exist
if (-not (Test-Path $sshDir)) {
    New-Item -ItemType Directory -Path $sshDir -Force
}

# Append jumpbox public key to authorized_keys
Get-Content "C:\temp\jumpbox_internal.pub" | Add-Content $authKeysFile

# 4. Set proper ACL permissions (CRITICAL for Windows OpenSSH)
# Windows OpenSSH requires specific permissions or it ignores the file
icacls $authKeysFile /inheritance:r
icacls $authKeysFile /grant "SYSTEM:(F)"
icacls $authKeysFile /grant "Administrators:(F)"

# 5. Update sshd_config to use administrators_authorized_keys
$sshdConfig = "C:\ProgramData\ssh\sshd_config"
$configContent = Get-Content $sshdConfig

# Ensure the Match Group line is configured
if ($configContent -notmatch "Match Group administrators") {
    Add-Content $sshdConfig @"

Match Group administrators
    AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys
"@
}

# 6. Restart SSH service to apply changes
Restart-Service sshd

# 7. Cleanup
Remove-Item "C:\temp\jumpbox_internal.pub" -Force

Write-Host "Windows SSH configuration complete"
Write-Host "Jumpbox can now SSH to this Windows VM"
```

### Phase 6: Fallback & Recovery Mechanism

The S3-based key exchange introduces potential failure points. This section defines detection, retry logic, and recovery procedures.

#### Failure Scenarios

```
┌─────────────────┐         ┌─────────────────┐         ┌─────────────────┐
│    Jumpbox      │         │       S3        │         │  Team Server    │
│                 │         │                 │         │                 │
│ 1. Generate key │         │                 │         │                 │
│ 2. Upload pub → │────X────│  ❌ FAILS!      │         │                 │
│                 │         │  (network/IAM)  │         │                 │
│                 │         │                 │         │ 3. Waiting...   │
│                 │         │                 │         │    forever...   │
└─────────────────┘         └─────────────────┘         └─────────────────┘
```

| Scenario | Cause | Impact | Detection |
|----------|-------|--------|-----------|
| **S3 Upload Failure** | Network issue, IAM permissions | Team Server waits forever | CloudWatch S3 error metrics |
| **S3 Download Timeout** | Key not uploaded, wrong path | Instance stuck in bootstrap | Instance health check fails |
| **IAM Permission Denied** | Missing policy, wrong role | All S3 operations fail | CloudTrail access denied logs |
| **Key Corruption** | Partial upload, encoding issue | SSH auth fails silently | Manual SSH test fails |

#### Retry Logic with Exponential Backoff

**Updated jumpbox_init.sh with retry logic:**
```bash
#!/bin/bash
set -e

LOG_FILE="/var/log/key-bootstrap.log"
exec > >(tee -a "$LOG_FILE") 2>&1

# Configuration
MAX_RETRIES=5
INITIAL_DELAY=5
MAX_DELAY=60

# Function: Upload with exponential backoff
upload_with_retry() {
    local file="$1"
    local s3_path="$2"
    local attempt=1
    local delay=$INITIAL_DELAY
    
    while [ $attempt -le $MAX_RETRIES ]; do
        echo "[$(date)] Attempt $attempt/$MAX_RETRIES: Uploading $file to $s3_path"
        
        if aws s3 cp "$file" "$s3_path" --region ${aws_region} 2>&1; then
            echo "[$(date)] SUCCESS: Key uploaded to S3"
            return 0
        fi
        
        echo "[$(date)] FAILED: Upload attempt $attempt failed, retrying in ${delay}s..."
        sleep $delay
        
        # Exponential backoff with jitter
        delay=$((delay * 2 + RANDOM % 5))
        [ $delay -gt $MAX_DELAY ] && delay=$MAX_DELAY
        attempt=$((attempt + 1))
    done
    
    echo "[$(date)] CRITICAL: All upload attempts failed after $MAX_RETRIES tries"
    return 1
}

# 1. Generate jumpbox's internal key pair
echo "[$(date)] Generating Ed25519 key pair..."
ssh-keygen -t ed25519 -f /home/ubuntu/.ssh/jumpbox_internal_key -N "" -C "jumpbox-internal"
chmod 600 /home/ubuntu/.ssh/jumpbox_internal_key
chmod 644 /home/ubuntu/.ssh/jumpbox_internal_key.pub
chown ubuntu:ubuntu /home/ubuntu/.ssh/jumpbox_internal_key*

# 2. Upload PUBLIC key to S3 with retry
S3_KEY_PATH="s3://${deployment_bucket}/keys/${deployment_id}/jumpbox_internal.pub"

if ! upload_with_retry "/home/ubuntu/.ssh/jumpbox_internal_key.pub" "$S3_KEY_PATH"; then
    # Signal failure to CloudWatch
    aws cloudwatch put-metric-data \
        --namespace "GOAD/Bootstrap" \
        --metric-name "KeyUploadFailure" \
        --value 1 \
        --dimensions DeploymentId=${deployment_id} \
        --region ${aws_region} || true
    
    # Write failure marker for debugging
    echo "KEY_UPLOAD_FAILED" > /opt/bootstrap-status
    exit 1
fi

# 3. Signal success
aws s3 cp - "s3://${deployment_bucket}/status/${deployment_id}/jumpbox-ready" \
    --region ${aws_region} <<< "ready"
echo "KEY_UPLOAD_SUCCESS" > /opt/bootstrap-status

echo "[$(date)] Bootstrap complete - key exchange successful"
```

**Updated teamserver_init.sh with timeout:**
```bash
#!/bin/bash
set -e

LOG_FILE="/var/log/key-bootstrap.log"
exec > >(tee -a "$LOG_FILE") 2>&1

# Configuration
MAX_WAIT_TIME=600  # 10 minutes max wait
POLL_INTERVAL=10
S3_KEY_PATH="s3://${deployment_bucket}/keys/${deployment_id}/jumpbox_internal.pub"

echo "[$(date)] Waiting for jumpbox public key..."

start_time=$(date +%s)
while true; do
    current_time=$(date +%s)
    elapsed=$((current_time - start_time))
    
    # Check timeout
    if [ $elapsed -ge $MAX_WAIT_TIME ]; then
        echo "[$(date)] CRITICAL: Timeout waiting for jumpbox key after ${MAX_WAIT_TIME}s"
        
        # Signal failure
        aws cloudwatch put-metric-data \
            --namespace "GOAD/Bootstrap" \
            --metric-name "KeyDownloadTimeout" \
            --value 1 \
            --dimensions DeploymentId=${deployment_id} \
            --region ${aws_region} || true
        
        echo "KEY_DOWNLOAD_TIMEOUT" > /opt/bootstrap-status
        exit 1
    fi
    
    # Try to download key
    if aws s3 cp "$S3_KEY_PATH" /tmp/jumpbox_internal.pub --region ${aws_region} 2>/dev/null; then
        echo "[$(date)] SUCCESS: Downloaded jumpbox public key"
        break
    fi
    
    echo "[$(date)] Key not available yet, waiting... (${elapsed}s elapsed)"
    sleep $POLL_INTERVAL
done

# Validate key format
if ! ssh-keygen -l -f /tmp/jumpbox_internal.pub > /dev/null 2>&1; then
    echo "[$(date)] CRITICAL: Downloaded key is invalid or corrupted"
    echo "KEY_INVALID" > /opt/bootstrap-status
    exit 1
fi

# Add to authorized_keys
mkdir -p /home/ubuntu/.ssh
cat /tmp/jumpbox_internal.pub >> /home/ubuntu/.ssh/authorized_keys
chmod 600 /home/ubuntu/.ssh/authorized_keys
chown -R ubuntu:ubuntu /home/ubuntu/.ssh
rm /tmp/jumpbox_internal.pub

echo "KEY_CONFIGURED" > /opt/bootstrap-status
echo "[$(date)] Bootstrap complete - SSH access configured"
```

## Security Benefits

### Key Algorithm: Ed25519 vs RSA

This architecture uses **Ed25519** keys instead of RSA. Here's why:

```bash
# Recommended key generation command:
ssh-keygen -t ed25519 -f ~/.ssh/goad_user_key -C "user@goad-deployment"
```

| Algorithm | Key Size | Security Level | Performance | Recommendation |
|-----------|----------|----------------|-------------|----------------|
| **Ed25519** | 256 bits | 128-bit equivalent | ⚡ Fastest | ✅ **Recommended** |
| RSA 4096 | 4096 bits | 128-bit equivalent | Slower | Legacy systems only |
| RSA 2048 | 2048 bits | 112-bit equivalent | Moderate | ❌ Avoid (weak) |
| ECDSA | 256-521 bits | 128-256 bit | Fast | ⚠️ Avoid (NIST curves) |

**Why Ed25519:**
- **Smaller keys** = faster SSH handshakes and less bandwidth
- **No weak key generation** = impossible to accidentally create weak keys
- **Side-channel resistant** = harder to extract via timing attacks
- **Deterministic signatures** = no random number generator vulnerabilities
- **Universal support** = OpenSSH 6.5+ (2014), all modern systems

**Terraform State Note:** Even with private keys removed from state, use encrypted remote backend:
```terraform
terraform {
  backend "s3" {
    bucket         = "your-terraform-state-bucket"
    key            = "deployments/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true                    # Enable server-side encryption
    kms_key_id     = "alias/terraform-key"   # Optional: use KMS for encryption
    dynamodb_table = "terraform-locks"       # Enable state locking
  }
}
```

### Before (Current) vs After (Proposed)

| Aspect | Current | Proposed |
|--------|---------|----------|
| **Private Key Generation** | Terraform (central) | Each host (local) |
| **Private Key Storage** | Terraform state, API | Host filesystem only |
| **Private Key Transmission** | API, user_data | Never transmitted |
| **User Key Management** | Terraform-generated | User's own key pair |
| **Terraform State** | Contains sensitive keys | No sensitive keys |
| **API Exposure** | Returns private keys | Returns connection info only |
| **SSH Best Practices** | ❌ Violated | ✅ Compliant |
| **Compromise Impact** | All keys exposed | Isolated per host |

### Additional Security Improvements

1. **Key Rotation**: Each deployment uses fresh keys, automatically discarded on teardown
2. **Least Privilege**: Each host only has keys it needs for its role
3. **Audit Trail**: S3 key exchange logged via CloudTrail
4. **No Shared Secrets**: Each deployment is cryptographically isolated

## C2-Only Deployments

For **C2-Only** deployments (no GOAD lab), access goes through the Dashboard Server — there is no per-deployment SSH-relay bastion:

```
User Workstation
    │
    │ ssh -i ~/.ssh/user_key ubuntu@dashboard-eip
    │
    ▼
Dashboard Server (own VPC, EIP) ── VPC peering ──> Team Server (Private)
    │  (server's internal public key on each instance)
    │
    └──────────────────────────────────────────────> Redirectors (Private)
                                                      (server's internal public key)
```

**Key Points:**
- User provides their public key before deployment (authorizes to the Dashboard Server)
- The Dashboard Server uses its own internal key pair, distributed via SSM, to reach each instance
- Team servers and redirectors receive the Dashboard Server's internal public key
